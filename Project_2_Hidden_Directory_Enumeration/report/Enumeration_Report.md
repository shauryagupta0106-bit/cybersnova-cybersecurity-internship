## 1. Introduction

Web applications may expose directories and files that are not linked directly from their homepages. These resources may include application pages, static assets, server-generated content, administrative interfaces, or configuration-related resources.

Hidden directory and file enumeration is a reconnaissance technique used to identify candidate web paths by sending HTTP requests with words from a predefined wordlist. The server's responses help determine which paths may exist and which resources deserve further investigation.

This project was conducted against the assigned training target, `http://testasp.vulnweb.com/`, using Gobuster, Dirsearch, Dirb, and curl in Kali Linux.

The assessment identified multiple directory paths, ASP application endpoints, and a robots.txt file. Selected findings were subsequently checked using read-only HTTP requests to compare enumeration results with observed server responses.

The report documents the actual findings, limitations, and evidence available from the assessment.

## 7. Findings and Verification Analysis

### 7.1 Directory redirects

Several discovered paths returned HTTP 301 during enumeration. The redirect destinations generally added a trailing slash, for example:

`/cgi-bin` to `/cgi-bin/`

This behavior is consistent with URL normalization. It does not independently indicate a security weakness.

### 7.2 Access-restricted directories

The verification requests returned HTTP 403 for:

- `/cgi-bin/`
- `/images/`
- `/templates/`
- `/aspnet_client/`

These responses indicate that the server denied the tested requests. The evidence does not establish whether access would differ under other legitimate application contexts, but no directory listing or sensitive file was demonstrated.

### 7.3 The `/_vti_cnf/` directory

The path was discovered by the enumeration tools and returned HTTP 200 during verification, with a response size of 926 bytes.

This is a candidate for additional review because the path name is associated with FrontPage-related metadata in some web-server environments. However, the path name and HTTP status alone do not prove that this particular resource contains sensitive information.

**Evidence-supported conclusion:** The resource returned an HTTP 200 response. Its actual body must be examined before assigning a vulnerability or severity rating.

### 7.4 Application endpoints

The following endpoints returned HTTP 200 during verification:

- `/search.asp`
- `/login.asp`
- `/register.asp`
- `/default.asp`

These are application endpoints rather than automatically confirmed vulnerabilities. Their presence is expected for many web applications.

The assessment did not include detailed application testing of input validation, authentication, authorization, session management, or business logic.

### 7.5 The `db.asp` endpoint

The endpoint returned HTTP 200 but delivered a zero-byte response.

An empty response does not demonstrate that database credentials, database contents, or internal configuration are exposed. Further conclusions would require additional evidence.

### 7.6 Incomplete Dirb scan

The later Dirb scan encountered connection errors and a possible DNS resolution problem. As a result, its findings cannot be treated as a complete enumeration.

The results remain useful as partial observations, but the report does not claim that every directory or file on the target was identified.

## 9. Recommendations

The following recommendations are defensive measures relevant to the types of resources identified during this assessment.

1. **Review `/_vti_cnf/`.** Examine its response body and determine whether it contains internal metadata or other information that should not be public.
2. **Restrict unnecessary resources.** Remove or restrict obsolete directories, unused application endpoints, and unnecessary server components.
3. **Prevent unintended directory listings.** Verify that directory indexing is disabled where it is not required.
4. **Protect sensitive files.** Keep configuration files, backups, database credentials, and temporary files outside publicly served directories.
5. **Review authentication and authorization.** Ensure that login, registration, and other application functions enforce the intended access controls.
6. **Validate session handling.** Confirm that logout operations invalidate the appropriate session state rather than relying only on a redirect.
7. **Monitor web-server responses.** Review logs for suspicious requests and repeated enumeration attempts where appropriate.
8. **Repeat verification when necessary.** Confirm important findings with direct requests and retain timestamps and response evidence.
9. **Document limitations.** Record incomplete scans, timeouts, and connection failures rather than interpreting missing results as proof that resources do not exist.

These recommendations do not imply that every listed weakness was present on the target.

## 10. Limitations

The findings are limited to the paths tested, the wordlists used, the tool configurations, the responses received, and the assessment period.

The following limitations apply:

- Enumeration may miss paths that are absent from the selected wordlists.
- HTTP responses may vary over time or with server configuration.
- HTTP 200 indicates a successful HTTP response, not that a resource is safe or vulnerable.
- HTTP 301 indicates a redirect, not necessarily a security issue.
- HTTP 302 indicates a temporary redirect, not proof of successful logout or session invalidation.
- HTTP 403 indicates denial of the tested request, not proof that every access route is blocked.
- Case variations may resolve to equivalent content or distinct resources. The supplied results do not establish which applies to every variant.
- The nested `/aspnet_client/system_web/` path was discovered, but its HTTP status was not supplied.
- The later Dirb scan was incomplete because of connection errors.
- The actual response body for `/_vti_cnf/` was not included in the supplied verification output.
- No successful exploitation or confirmed disclosure of sensitive information was demonstrated.

Accordingly, this report documents enumeration and selected response verification, not a comprehensive penetration test.

## 11. Summary and Conclusion

This project used Gobuster, Dirsearch, and Dirb to identify candidate directories and application endpoints on `http://testasp.vulnweb.com/`.

The recorded outputs identified directory paths such as `/cgi-bin/`, `/images/`, `/templates/`, `/aspnet_client/`, `/_vti_cnf/`, `/html/`, `/t/`, `/avatars/`, and `/jscripts/`, together with multiple capitalization variants. ASP endpoints included `/search.asp`, `/login.asp`, `/register.asp`, `/logout.asp`, `/default.asp`, and `/db.asp`. The assessment also identified `robots.txt`.

The subsequent curl verification confirmed several HTTP responses. Four tested directories returned HTTP 403, while `/_vti_cnf/` returned HTTP 200 with a 926-byte response. The login, registration, search, and default application endpoints returned HTTP 200. The logout endpoint returned HTTP 302 and redirected to `/Default.asp`. The `db.asp` endpoint returned an empty response body.

The most important follow-up candidate is `/_vti_cnf/`, because its contents have not yet been reviewed. The evidence does not establish that this resource contains sensitive data, so it would be inappropriate to label it a confirmed vulnerability.

The project demonstrates the use of wordlists, enumeration tools, HTTP status codes, response verification, and evidence-based reporting. It also illustrates why raw tool output must be interpreted carefully and why incomplete scans should be documented honestly.

**Final conclusion:** Multiple candidate web paths were identified and selected responses were verified. No confirmed security vulnerability was established from the supplied evidence alone. Further content inspection and authorized application testing would be required to establish any actual security impact.
